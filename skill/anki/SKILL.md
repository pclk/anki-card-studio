# Anki cards

You write **highly descriptive, image-rich Anki flashcards** from the user's material with `scripts/anki_helper.py`. The output is **`anki_bundle.json`** (cards and all images). The user drops it into **Anki Card Studio** to review every card, request changes and export an `.apkg`.

## Settings

The user's message (usually generated by the Studio's Prompt tab) may set these. Use the defaults for anything unset.

| Setting | Default |
|---|---|
| What to cover | everything important in the material |
| Deck name | `AI Generated Deck` (`::` for sub-decks) |
| Number of cards | as many as the key ideas need, no filler |
| Card types | Basic **and** Cloze, chosen per fact |
| Learner level | a motivated student new to the topic |
| Language | English |
| Detail | **descriptive** (rule 1) |
| Images | generated diagrams + confirmed Wikimedia photos + figures from the material, only where they help (rule 4) |
| Tags | none |
| Card order | anti-spoiler order (rule 11) |
| Source locations | `ref` on every card (rule 6) |

## Workflow

1. **Load the helper.**
   - **Claude Code or any machine with Python:** write `build_deck.py` in the working folder, starting with `import sys; sys.path.insert(0, "<this skill's dir>/scripts"); from anki_helper import *`. Run it with `ANKI_OUT_DIR=anki_out uv run --with pymupdf --with pillow --with matplotlib --with latex2mathml python build_deck.py`. Keeping the build as a script makes fixes cheap: edit it and re-run it.
   - **claude.ai code sandbox:** `exec(open("<skill_dir>/scripts/anki_helper.py").read())`.
   - `help()` prints the API.
   - **Checker settings.** If the prompt has a "Checker settings" section, call `deck.configure_checks({...})` with it right after creating or loading the deck, and write the cards to those limits (minimum why length, maximum front length, cloze numbers, which checks are errors). Without one, the defaults apply. `deck.checks` shows the active settings; the values replace the defaults mentioned in the rules below.
2. **Get the material and read it before writing.**
   - **Attached files:** `list_uploads()`, `find_upload("name")`, `pdf_info`, `pdf_text`, `pdf_figures`, `office_images`.
   - **Google Drive link:** use a Drive connector if there is one. A public file downloads with `uvx gdown --fuzzy "<link>" -O <dir>/`. Otherwise ask for the file.
   - **Batch prompt:** the material is in `<<<SOURCE … SOURCE>>>` (see below).
   - **Always** call `deck.load_source(...)` with whatever the refs will point into, so `validate()` can check every quote: the PDF paths (no argument = every uploaded PDF), or the SOURCE block's id (see below).
   - **Never retype a block of the prompt into code.** The Studio's blocks carry an id (`<<<SOURCE id=s-1a2b3c4d`, `<<<REVISE_CARDS id=r-…`); pass just the id and the helper reads the block from the prompt saved as a file (an attachment, the working folder or `~/Downloads`). If it reports that no file has it, ask the user to send the prompt as a file (Studio: tick **📎 As a file** before copying) rather than copying the text into your code.
   - **Plan first:** concepts → card type → image. Only then write cards.
3. **Write the cards** with `deck.add_basic` / `deck.add_cloze` and the HTML helpers (`answer`, `box`, `img`, `bullets`, `table`, `code`, `tex`). Image functions *return* the filename to use, and extensions can change, so always use the returned name.
   - Give cards `name=` handles and use those names, never list positions: `ids["chain_rule"] = deck.add_cloze(..., name="chain_rule")`. Names work in `set_order`, `prereq=`, `update` and `delete`.
   - Give every card an **extensive** `why=`, built with `rationale()`. The user reads it while reviewing to judge whether the card earns its place, and can put it on the card as a collapsible "Why this card" section. Write each part as 1–3 full sentences specific to this card, never generic filler ("this is an important concept"). Aim for roughly 60–150 words:
     ```python
     why=rationale(
         tests="Whether you can tell that assigning an Integer[] to an Object[] compiles AND runs - a complete answer names array covariance as the reason.",
         matters="Covariance is what lets a later `objArray[0] = \"Hello\"` compile and then throw ArrayStoreException; PE questions mix these cases to test whether you separate compile-time and run-time checks.",
         mistake="Treating arrays like generics: List<Integer> is NOT a subtype of List<Object>, so students wrongly predict a compile error here.",
         connects="Builds on subtyping (L04); the run-time half is the next card, and generics' invariance (L07) is the contrast.")
     ```
     `validate()` warns when a why is missing or under ~45 words.
4. **`deck.validate()` and fix everything.** `ERROR`s must be fixed; read every `warn` and fix it unless it's clearly fine. Re-run until it's clean.
5. **Look at every image. This step is not optional.** Run `deck.contact_sheet()` (and `deck.preview_png()` for the cards) and **open each PNG it prints with your image-viewing tool**: the file view tool in Claude Code, the image viewer in claude.ai. Generating the sheet without opening it doesn't count. For every image check:
   - elements overlapping or covering each other (labels on labels, labels across boxes or lines, crowded axis labels)
   - anything cut off at the edges, text too small to read, empty or near-empty images
   - wrong content (a label pointing at the wrong part, a diagram that doesn't match the card)

   Redraw what's wrong (more space, shorter labels, fewer elements, a bigger figure) and look again. `figure()` measures every matplotlib figure and reports overlapping text and boxes, and `validate()` stays red until the overlaps are fixed and every new image has been on a contact sheet or preview. Those checks only catch some problems; your own look is the real check.
6. **Study order:** `order = deck.suggest_order()`, adjust if needed, `deck.set_order(order)`, then `deck.check_order()` (rule 11).
7. **`deck.save()`.** It prints the full path of `anki_bundle.json`.
   - **claude.ai:** it lands in `/mnt/user-data/outputs`; hand that file over.
   - **Claude Code:** it lands in `ANKI_OUT_DIR` (default `./anki_out`).
   - If the chat can't hand over files at all, use `deck.save(print_block=True)` and give the `<<<ANKI_CARDS` block instead.
8. **Your entire reply** is `print(deck.summary(issues))`, exactly in this shape and nothing else (no tables, no commentary):
   ```
   Deck generated: {deck name}
   Total cards: {number of cards}
   Number of Basic cards: {number}
   Number of Cloze cards: {number}
   Number of Images: {number}
   Unexpected and unresolvable issues: {issues}
   ```
   `issues` lists only what you could **not** resolve, in short phrases; "None" if nothing.

Without any code tool, write the bundle JSON by hand (format at the end). Every `<img>` must then be a `url` (confirmed Wikimedia) or `material` media entry. Finish with the same summary.

## Card-writing rules

1. **One question per card, rich answers.** Each card asks exactly ONE question and tests ONE idea; the back teaches it.
   - Never bundle several questions on one front: no numbered sub-questions, "classify each of these", "for each statement…", or a back of the form "1 → A; 2 → C; 3 → B". Make one card per item. Each card restates the shared instructions, so it stands alone. Example: instead of one card classifying four Java statements as compile error / run-time error / runs, write four cards like "`Object[] objArray = intArray;` (intArray is an `Integer[]`). Rejected at compile time, compiles but fails at run time, or compiles and runs?" → "**Compiles and runs.** Arrays are covariant, so `Integer[] <: Object[]`." Give them the same `group=` so the study order spaces them.
   - A single question whose answer is a list ("What are the 4 steps of…?") is fine. So is a genuine whole-set task (put these in order, match these pairs); tag it `multi-ok`. `validate()` flags bundled questions as errors.
   - *concise*: the answer plus at most one line of context.
   - *descriptive* (default): `answer()` in one bold line, then a short WHY/HOW (2–4 sentences or bullets), then an example or application where relevant.
   - *deep*: as descriptive, plus a comparison with easily confused concepts and a pitfall or mnemonic. Put the secondary depth in `extra`.
2. **Specific, self-contained cards: the card carries everything needed to answer it.** The person reviewing has *only this card* in front of them: not the notes, not the slides, not the other cards, and they won't remember the exact code from the lecture. So:
   - Name the subject; no "it", "this" or "the above". Never point elsewhere ("as in the previous card", "the example above", "Figure 3", "from the lecture", "in L04").
   - If the question is about specific code, **show that code on the front** in a `code()` block: the class, method signature and the lines that matter, cut down to what's needed. Bad: "During `p1.distanceTo(p2)`, what do `this` and `q` point to, and what happens if the method mutates `q`'s object?" (`q` is `distanceTo`'s parameter, which the card never shows, so it tests recall of the notes, not the concept). Good: the front shows `double distanceTo(Point q) { return Math.hypot(q.x - this.x, q.y - this.y); }` and then asks about `p1.distanceTo(p2)`.
   - Same for any named variable, parameter, field, table or figure the question relies on: define it on the card. Standard library calls (`list.add`, `stream.map`) need no definition.
   - `validate()` flags references to outside material as errors and calls to code the front doesn't show as warnings. Tag a card `refs-ok` only when the reference is genuinely self-explanatory.
   - Prefer why/how/compare/apply over bare recall. Cover definitions, mechanisms, classifications, numbers and exceptions.
3. **Cloze** suits definitions, key sentences, short lists and formulas.
   - Use 1–3 deletions per note, with one concept per deletion: `{{c1::Product}}, {{c2::Price}}`.
   - Use the same number to hide things together.
   - Add a hint (`{{c1::answer::hint}}`) when the blank would be ambiguous.
   - Never cloze trivial words. Explanations and images go in `extra`.
4. **Images: only where they genuinely help** understanding or recall. There's no quota.
   - Every image gets a figcaption that says what to look at.
   - Never reuse an image as filler.
   - Never put an image on a card if its labels give away another card's answer (`check_order` flags images shared between nearby cards).
   - **Generated:**
     - `flowchart` (processes; boxes size to their text and long chains wrap into rows)
     - `concept_map` (classifications)
     - `graph` (dependencies / flows with labelled arrows, automatic layout)
     - `table_image` (comparisons; prefer the HTML `table()` when cells are short)
     - `timeline`
     - `labeled_image` (`numbered=True` for "identify the structure" cards)
     - `deck.figure(fig)` for any matplotlib plot. Missing glyphs are caught: use mathtext (`r"$\perp$"`) or plain words instead of exotic Unicode.
   - **Real photos are optional.** If no real photo suits the topic, leave photos out even when the settings allow them.
     - Use `web_image("https://commons.wikimedia.org/wiki/Special:FilePath/<Exact_File_Name.ext>?width=800", …)` only with a file name you have **confirmed exists** (WebSearch / WebFetch the file page). Never guess one; the shell usually can't reach Wikimedia to check.
     - `deck.check_web_images()` verifies them when the network allows.
   - **From the material:**
     - `pdf_figure(p, page, index)` for embedded figures with their labels
     - `crop_pdf(p, page, box)` for any region, including vector diagrams; `render_page_preview` gives a grid for choosing the box
     - `office_image`
     - `add_image_file`
     - If you can't crop reliably, use `material(name, hint="file p.N - which figure")`.
5. **Source** field: human-readable origin, e.g. `lecture3.pdf p.12`, or `<page title> - <URL>` for a web source.
6. **`ref` on every card**, so the Studio can show the source passage inside the card: `ref=("lecture3.pdf", 12, "verbatim quote")` (a list for several sources).
   - **File name:** use it exactly as it appears in the attachment or in the `[name p.N]` markers.
   - **Quote:** pick the sentence that states the fact, at least ~25 characters. `validate()` reports a quote missing from its page, and where it actually is.
   - **What "verbatim" means:**
     - **PDF:** matches the PDF's text layer: the words as `pdf_text()` / the SOURCE text gives them. Case and whitespace don't matter; spelling and word order do.
     - **Slides / DOCX / extracted text:** copy from the SOURCE / extracted text.
     - **Markdown or web text:** match the *rendered* text, without `*`, `#`, backticks or link syntax.
     - **Scanned or image-only PDFs** (no text layer) and text recovered by OCR: quote the recovered text you were given and note "no text layer" in `extra`. Highlighting won't work for these, but the page picture still will. A note in the material saying "don't quote" refers to *the card's wording*; the ref quote is only a locator and stays verbatim.
   - **Web sources:**
     - `source` = page title + URL.
     - `ref=(URL or the source name used in the markers, section_number_or_0, quote)`. The section is the `p.N` of the marker; use 0 if unknown and the Studio searches the whole page.
7. **Accuracy first.** State only what the material supports or what is well established; flag uncertainty in `extra`. No duplicate cards.
   - **Errors in the source:** teach the correct value. Add a `box("warning", "The slides print X; the correct value is Y because …")` to that card, never cloze the wrong value, and list the correction under "Unexpected and unresolvable issues" in the summary (e.g. "L03 p.7 prints 2^10=1000; cards use 1024").
8. **HTML.** Allowed tags: `b strong i em u s sub sup br hr p div span ul ol li table thead tbody tr th td pre code img figure figcaption mark small h3 h4 a blockquote kbd`.
   - **Never set colours or backgrounds** (`style="background:…"`, `color:…`). Cards show in light **and** night mode; a white or light background makes text unreadable at night. The note type already styles everything.
   - Escape text with `esc()`: `x &lt; 5`, never a raw `<` or `&`.
   - Styled blocks come only from the helpers:
     - `answer()` → `aa-answer`
     - `box(kind)` → `aa-box aa-{key|why|example|method|check|mnemonic|warning|note|compare|clinical}`; other kinds raise
     - `img(name, caption)` → `aa-fig`
9. **Code:** `code(text, "java")` gives `<pre><code class="language-java">…`, escaped. The Studio highlights it and bakes the colours into the export, so don't style it yourself. Use `code(x, inline=True)` for inline code.
   - Example front: `"What does this print?" + code("int x = 5;\nSystem.out.println(x++ + ++x);", "java")`
   - **Every code-block line fits a phone: at most 27 characters** (`code_line_chars`; the width of `public ColoredCircle(Circle`). Break long lines at natural points (after a comma or operator, one chained call per line, parameters on their own lines) and indent the continuation; use short but meaningful names. This limit is for code blocks only, not prose, inline code or maths.
   - Example back: `answer("12") + box("why", "x++ yields 5 then x=6; ++x makes x=7 and yields 7; 5+7=12.")`
10. **Maths:** write LaTeX. `tex(r"\frac{dy}{dx}")` → `\(\frac{dy}{dx}\)` and `tex(…, display=True)` → `\[ … \]`; plain `$…$` / `$$…$$` in card text also works (the helper converts it on add and save; "$5" money is left alone). Anki, the Studio and `preview_png()` all render it (the preview offline, via MathML).
    - Clozes can sit inside a formula: `$x = {{c1::\frac{1}{2}}}$`; Anki and the previews show the gap in the formula. The helper spaces LaTeX's own `}}` so they can't close a cloze early; `cloze()` does the same.
    - `validate()` checks every formula: unbalanced braces, LaTeX that doesn't parse, and unknown commands (MathJax would show them in red).
    - Diagram labels take `$…$` too (matplotlib mathtext: `\frac`, `^ _`, `\sqrt`, Greek, `\sum`, `\int`, `\mathrm` …, but no environments such as `pmatrix`/`aligned` and no `\text`; put those in the card text). A formula is never split across lines when a label wraps.
    - Plain Unicode (×, ≤, π) is fine for simple expressions.
11. **Anti-spoiler study order.** Write cards grouped by topic; set the *study* order separately.
    - `suggest_order()` interleaves topics (`group=`, else the first tag), keeps `prereq=` cards first, and avoids a card showing the answer to one within the next 3.
    - `check_order()` explains any remaining spoilers: shared answer terms, numbers, the same image.
    - The Studio can show both orders, and exports yours as Anki's new-card order.

## Worked examples / problem decks

When the material is problems or worked solutions, test the **method and the reason**, not just the final answer:
- **One card per sub-part.** Front: the problem (or sub-part). Back:
  - `answer()`
  - `box("method", bullets(steps, ordered=True))`: the key moves, each with its reason
  - `box("check", "…")`: how to verify the result (substitute back, units, a limiting case, an estimate)
- **Method cards:** cloze or basic cards for the general technique, e.g. "To find stationary points, first {{c1::set f'(x)=0}}".
- **Spacing:** keep cards that share numbers or a worked example **apart** in the study order. A method card's worked example can give away a later problem card; give those cards `prereq=`/`group=` so `suggest_order` spaces them, and check with `check_order()`.

## Attached source files (the Studio's prompts)

The Studio attaches the original files (PDF, slides, Word) rather than only their text. A batch part gets only its own pages of a PDF, as an excerpt such as `L01_p12-30.pdf`; the prompt says which pages it holds.
- Read and crop from the attachments like any upload (`pdf_info`, `pdf_text`, `pdf_figures`, `deck.pdf_figure`, `render_page_preview`, `office_images`).
- **Cite the original file and page**, never the excerpt's own numbering: `orig_page(path, n)` gives `(file, page)`, and `pdf_info` shows both.
- `deck.load_source(path)` for each attachment: an excerpt's page map is read from the file, so `validate()` checks quotes against the original pages. Slides and Word files are read too.
- A part that got a whole slide deck covers only the slides the prompt names.

## Batch prompts (the Studio's "Source material" prompts)

A batch prompt with no attachments carries its material between `<<<SOURCE` and `SOURCE>>>`, with markers like `[L01.pdf p.12]` (pasted text and web pages always come this way).
- `deck.load_source("s-…")` with the id on the `<<<SOURCE id=…` line, so quotes are checked against it. If no file has the block, skip it (quotes then go unchecked) and say so in the summary; don't retype the text.
- `source` and `ref` take the file and page of the nearest marker above the fact.
- Use the deck name and id prefix the prompt gives: `Deck("CS2030S::L01 …", id_prefix="L01-c")`.
- You can't crop figures here. Where a `[figure on this page]` marker shows a figure would help, use `material(name, hint="L01.pdf p.12 - the class diagram")`. Generated diagrams and confirmed photos are fine.
- Finish with the same summary.

## Batch planning ("batch planning workflow")

The user attaches a lot of material and wants **anki_prompts.json**: one self-contained prompt per part, each pasted into its own chat. **Don't write cards and don't retype the material**; the scripts move the text.

1. `uv run <skill_dir>/scripts/extract.py <files or folder> -o extract.json --outline`. It prints pages, ~tokens and the first line of every kept page, after dropping headers, footers, page numbers and slide builds. Plan from that outline, and read the full text only where you must.
2. **Split as asked:**
   - **"One prompt per file":** run `make_prompts.py extract.json --per-file --deck-root "<parent>" [--max-pages N] -o anki_prompts.json`.
   - **Otherwise:** write a small `plan.json`: `{"deck_root": "...", "items": [{"id": "L01", "title": "...", "focus": "1-3 sentences", "count": 25, "sources": [{"file": "L01.pdf", "pages": "1-18"}]}]}`. Then run `make_prompts.py extract.json --plan plan.json -o anki_prompts.json`.
   - Keep ids short; they become card-id prefixes. Keep each item at most ~40k tokens. Give every item a `focus`.
3. Fix the plan until the script reports no important page uncovered.
4. Deliver `anki_prompts.json` with a short table: id · title · ~tokens.

## Revisions (from the Studio's Revise tab)

The user pastes a `<<<REVISE_CARDS … REVISE_CARDS>>>` block. Each card has its current content, including the user's own edits, and a `feedback`.
1. `deck = Deck.load("r-…")` with the id on the `<<<REVISE_CARDS id=…` line (never retype the block), then read `deck.feedback` and `deck.show()`.
2. Apply the feedback with `deck.update(id, ...)`, `add_basic/add_cloze(..., after="c007")` for splits or new cards, and `deck.delete(id)`.
   - Keep ids; new ids must not appear in `existing_ids`.
   - A changed image gets a NEW filename.
   - New and split cards get their own extensive `why=` (`rationale()`); update a card's `why` when the change alters what it tests.
   - A card that bundles several questions is split into one card per question (rule 1) even when the feedback didn't ask.
   - A card that leans on something the reviewer can't see (code, a figure, a definition, another card) gets it put on the card (rule 2), even when the feedback didn't ask.
3. **"I don't understand this card"** feedback:
   - Fix the card if its wording caused the confusion.
   - **Always** write a step-by-step explanation of why the card says what it says, starting from what the learner already knows, with each step's reason and a small worked example where it helps: `deck.explain(id, markdown)`.
   - If it's one or two short explanations, put them in your reply.
   - If there are more, or they're longer than a reply should be, `deck.save_explanations()` writes **`anki_explanations.md`**. Hand that file over and mention it in one line.
4. "Something is broken": check every field, every image (`contact_sheet()`), the cloze syntax and the ref.
5. `deck.validate()`. "Registered but not used" is fine for images the user already has.
6. `deck.save(revision=True)` → **`anki_revision.json`**. Reply with one line per changed card (what changed), plus the explanations note if any.

**Formatting pass** (the prompt says so, and each card's feedback starts "Formatting pass"): the user has already reviewed these cards. Change only how they're written: code into `code()` blocks, long code lines broken to fit `code_line_chars`, names into inline `<code>`, missing code/definitions/equations onto the card (rule 2), maths into `tex()` (display for multi-line or long formulas, never inside `<code>`). Never change what a card tests, its answer, `why`, images or tags; never delete, merge or split. The feedback comes from automatic checks and can be wrong: leave fine cards out. Save only the cards you changed.

**Checker fix** (the prompt says so, and each card's feedback starts "Checker fix"): the user has already reviewed these cards; the feedback lists what the automatic checks found. Fix only those problems: write or extend `why` (`rationale()`, at least `why_min_words`), cut a front or answer to the limit (keep everything needed to answer it; move background into `why`), split a note with too many cloze numbers or a card that asks several questions (keep the original id for the first part, `after=` for the others, each with its own `why`), and give source references their page and a verbatim quote of at least `ref_quote_min_chars` from the material (if you don't have the material, leave them and say so). Keep what a card tests, its answer, images and tags; never delete or merge. The checks can be wrong: leave fine cards out. Save only changed and split-off cards.

**Image fix** (each card's feedback starts "Image fix"; the broken images are in `media` with `"broken": true` and the user's `problem`, when they wrote one): redo only those images. Work out what each should show from the card and the material, make a correct, legible replacement (redraw it with `deck.figure`/`labeled_image`, re-snip the right page region, or use `web_image` with a credit), give it a **NEW filename**, and point the card's `<img>` at it. Check them with `contact_sheet()` before saving. Change nothing else on the card; never delete, merge or split. If an image adds nothing, remove it from the card and say so. Then `deck.save(revision=True)`.

If asked to fill gaps, add cards for important uncovered concepts, continuing the numbering.

## What the checker looks for

`validate()` runs these card-quality checks with the settings from `configure_checks()` (defaults in brackets). Write cards that pass them first time. Tag `multi-ok` / `refs-ok` only when a flag is genuinely wrong.
- **why** [warn, ≥45 words]: `why=` is non-empty, and has at least the minimum words once HTML is removed.
- **front_max_chars** [300]: basic fronts, counting characters after removing `<pre>`, inline `<code>`, `\( … \)` / `\[ … \]` maths and tags.
- **back_max_words** [no limit]: words on the back (or cloze text + extra), code blocks and tags removed.
- **cloze_max_deletions** [3]: distinct `cN` numbers in one cloze note.
- **multi_question** [error]: basic cards. The front has 2+ numbered items (`<ol>`, or lines starting `1.` `2)` `(a)` `i.`) answered one by one on the back. Or the front has 2+ `?` outside code (a warning). Or the back maps 3+ numbered items (`1 → A; 2 → C…`).
- **outside_refs** [error]: the question says "previous/next/other card", "the example/code/figure … above" or "… from the notes/lecture/slides", "Figure 3", "Slide 12", "Listing 4", "Table 2", "as shown/defined in the lecture/notes", "in/from the notes/slides/lecture/textbook", or "from L04". The back and extra are only checked for references to other cards and "… above". "Question 3.1" / "Exercise 2" / "Example 4" labels are warnings.
- **unshown_code** [warn]: the question has no code block, but calls a method on a variable (`p1.distanceTo(p2)`) that isn't a common library method.
- **code_as_text** [warn]: outside code tags, any of: `foo(x);`, `int x = …`, `new Foo(`, `x -> …`, `List<Integer>`, `return …;`, or `public static …`. Also inline `<code>` with 2+ `;`, a line break, or `{ … }` over 40 characters, when the field has no code block.
- **code_language** [warn]: a `<pre>` without `language-…` (use `code(text, lang)`).
- **code_line_chars** [27]: the longest line of any `<pre>` code block, tags removed and tabs counted as 8 columns. Code blocks only.
- **unshown_math** [warn]: the question has no display maths, but cites an equation or result by number or position: "equation 3", "Eq. (2.1)", "Theorem 2", "Lemma 3.1", "Proposition/Corollary/Identity/Formula 5", "using/by/from (3)", or "the formula/theorem/derivation … above". State it on the card.
- **math_as_text** [warn]: outside code and maths, any of: a LaTeX command (`\frac`, `\sum`, `\alpha`, `\leq`, `\begin` …), a power (`x^2`, `e^{-x}`), a one-letter subscript (`a_1`, `x_{n+1}`), `sqrt(`, or `∑ ∏ ∫ √`. Also inline `\( … \)` with a `\\` line break (outside a matrix), an `align`/`aligned`/`gather`/`cases`/`array` environment, or over 80 characters: use `tex(…, display=True)`.
- **math_in_code** [warn]: inline `<code>` or a `<pre>` without `language-…` that holds `\( \)`, `\[ \]` or a LaTeX command (shown as raw LaTeX). Use `tex()`.
- **ref_quote_min_chars** [25] and **ref_page** [warn]: quotes long enough to find, and a page for file references.
- **unused_images** [warn] and **order_window** [3]: as before.
